== Budget check (CLAUDE.md: <=50MB peak RAM, <100ms for <=500KB, <500ms for 500KB-5MB) ==
  All measured latencies are 2-4 orders of magnitude under budget: worst real-file case 3.5ms
  (<<100ms), worst synthetic case (5MB dense PII) 26.0-26.6ms (<<500ms). Peak RSS 30.2-30.3MB,
  comfortably under the 50MB ceiling. WITHIN BUDGET, large margin on every tier.

  NOT checked here: the <=3% CPU budget, which the spec measures against a representative
  egress event stream over time, not a single-process latency run. `--scan` (recursive
  real-world corpus profiler + PDF-bomb process isolation, mirroring Go's) has now been
  ported to the Rust CLI — run it against a real corpus to check this budget tier directly.

== Comparison against the Go implementation (../../deliverables/benchmark_results.txt) ==
  Not a like-for-like corpus (Go's committed baseline predates several detectors being added —
  it shows 31 detectors/6 profiles against a 12-file text corpus; this run has 38/11 against
  today's 26-file corpus), so the per-corpus numbers aren't directly comparable. The synthetic
  dense-PII benchmarks ARE apples-to-apples (identical generated buffer, same shape):

    tier    Go (BenchmarkInspect*)         Rust (this port)         ratio
    8KB     541µs/op   (15.2 MB/s)         162-166µs/inspect (~47-48 MB/s)   ~3x faster
    500KB   29.36ms/op (17.5 MB/s)         2.7-2.8ms/inspect (~177-180 MB/s) ~10x faster

  The gap widens at 500KB because Go's GC and goroutine-pool dispatch cost is amortised worse
  than Rust's rayon dispatch once there's enough real regex work per detector to dominate.
  At the small end (200B in-process), the engine itself takes ~60-65µs; real small-file runs
  show higher per-file numbers (~200µs-1ms mean) because those include per-file disk I/O
  (open/read/close syscalls) on top of the engine's own work — expected on any real filesystem,
  present in the Go original too, not a Rust-specific inefficiency.
